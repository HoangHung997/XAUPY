## RC1-AUDIT-001 — P1 — impossible partial close blocks eligible break-even

Reproduction on the actual BrokerExecution service and position_decision policy:

- BUY position: volume 0.01, broker minimum 0.01, volume step 0.01.
- Entry 4197.0; original SL 4194.0; original risk 3.0; current bid 4200.0.
- AUTO mode; partial close 50% at 1R; break-even at 1R, offset 0.1.
- Two management evaluations with partial close enabled each produced zero queued actions and `VOLUME_BELOW_BROKER_MINIMUM`; `partial_intent` remained null.
- Control: disable only partial close, keeping quote, position and risk unchanged. The next evaluation queued `MODIFY_POSITION` with SL 4197.1.

Cause: position_decision returns PARTIAL_CLOSE before evaluating BE, dynamic TP and trailing. BrokerExecution then rejects the rounded partial volume. The next evaluation takes the same early-return path again. The existing server SL is not removed; the defect prevents otherwise eligible post-entry protection from advancing.

Source: `python/xaupy_engine/position_management.py:position_decision`, `trade_plan.py:volume_on_grid`, `broker_execution.py:_management_action/manage_positions`.

Required fix: validate partial feasibility before choosing it; when an impossible partial is skipped, continue evaluating independent protective actions. Record a bounded, explicit skip reason. Do not solve this by weakening broker minimum/step rules or widening stops. Add combined small-volume partial+BE/trailing/dynamic-TP regression cases and rejected/partial-fill cases.

## RC1-AUDIT-002 — P1 — backup restoration can revive revoked REAL permission while retaining AUTO

Reproduction used the real EngineServer dispatcher and SettingsStore, with a fake price-source dictionary labelled REAL (not a real account):

1. Explicitly select AUTO with permitted REAL settings and matching profile; create backup.
2. Revoke REAL through `settings_set`.
3. Observe mode=AUTO, trading_enabled=false, reason=USER_REAL_PERMISSION_REQUIRED, effective_allow_real=false.
4. Call `backup_restore` with only backup_id; no new execution confirmation.
5. Observe mode=AUTO, trading_enabled=true, empty blocker, effective_allow_real=true. The restored settings and profile both re-enable REAL.

The test created zero trade intents. It proves permission/gate reactivation, not a broker fill. A subsequent eligible signal is a separate event.

Cause: backup_restore restores safety preferences/profile verbatim and replaces execution.settings without forcing an execution review. SettingsDashboard.Restore_OnClick directly invokes the restore API without a separate confirmation of permission/risk changes.

Source: `python/xaupy_engine/settings.py:restore_backup`, `server.py:_maintenance_response`, `src/XAUPY.Desktop/SettingsDashboard.axaml.cs:Restore_OnClick`, `src/XAUPY.Ipc/MaintenanceApi.cs:RestoreBackupAsync`.

Required fix: keep live permission grants independent of imported/restored profile data, or require explicit current-account review before increasing permission. Restoration must not silently reactivate new entries. Show a before/after risk and permission preview, protect unsaved drafts, and add AUTO/revoked-REAL/restore/restart tests.

## UI completeness — current evidence, not blanket certification

The executed audit parsed all 172 rows of FIRST_RELEASE_FEATURE_MATRIX.csv:

| Scope stored in the matrix | Rows |
| --- | ---: |
| IMPLEMENTED_ISOLATED_REGRESSION_AND_UI_REVIEW | 147 |
| BROKER_UAT_AFTER_DELIVERY | 24 |
| WINDOWS_LOGON_AFTER_DELIVERY | 1 |

All 172 rows have READY_FOR_USER_TEST and share one release_evidence string. These are readiness classifications, not 172 independent end-to-end PASS results. Earlier `baseline` or `previous_release_status` fields are historical; they must not be misread as proof a now-implemented control is still a stub.

Source inspection confirms real handlers for manual execution, pending forms, profile save/load/versioning, file-based chart comparison, indicator settings, PNG/fullscreen and Backtest comparison. That does not remove the two reproduced behavior defects or substitute for checking every UI state.

Specific scope/UI caveats:

- Settings Bridge-mode ComboBox has exactly one option and no selection binding/handler. It displays the sole supported connection mode; it is not a working selector for alternative bridge implementations.
- Settings account login/mode and data-path fields are read-only projections. Folder buttons open folders; they do not implement data-store relocation or account-password login. MT5 authentication is through the already-running terminal.
- Arbitrary chart-asset comparison loads a CSV/JSON file. It is not a live arbitrary-symbol subscription from MT5.
- The all-symbol view does not grant all-symbol trading control. Execution is constrained to the connected symbol and strategy magic; this scope must be clear next to bulk operations.
- English localization is incomplete: raw Vietnamese chart MenuItem.Header and Window.Title values are not routed through the tagged LocalizationService mechanism. This is a source-inspection finding, not a new native language-switch test.

## Approved-image parity

**No 100% visual acceptance.** The existing CaptureAudit.cs creates one 1672x941 headless window, navigates ten tabs, supplies synthetic bars and empty positions/orders/deals, and keeps execution OFF. It saves screenshots/control bounds and checks the manual-confirmation/BUY placement on Orders. It does not load the approved PNGs or calculate approved-image differences; a green capture run is not a pixel-parity result.

There is also a requirement mismatch: docs/ui-reference/README.md permits non-pixel-identical native controls/spacing, while the user's latest request requires 100% matching to the agreed demo. The latest stricter user requirement must be explicitly reconciled in acceptance, rather than silently treating the permissive README as approval.

Image retrieval in this re-audit returned `Native image pixels were unavailable`; the local execution/container tool was unavailable. Therefore no new visual pixel review or interactive desktop run is claimed here. The new Python behavior reproducers above were run remotely on GitHub CI instead. No percentage of visual similarity is invented.

The remaining visual acceptance needs same-size/DPI/theme captures of the actual candidate, including populated tables, long text, dialogs, errors, draft states and scrolling. Dynamic account values, prices and trade results must not be fabricated to match demo values.

## MT5 readiness

The release contains real OrderCheck/OrderSend paths, account/symbol/magic ownership checks, broker lot/stop/freeze checks, persisted intent IDs and broker-result reconciliation. It is not merely the old manual simulator. Nevertheless, code existence and compilation do not establish successful behavior with the intended broker.

Known compatibility boundaries in EA source include no merging into an already-exposed netting symbol and pending requests requiring supported specified expiration. These should be presented before sending rather than interpreted as universally supported brokerage behavior.

Before full acceptance: fix both reproduced P1 defects, run their corrected regressions and the existing suite, produce a new versioned candidate, verify its exact package, then perform controlled DEMO broker acceptance for entry/close/pending/BE/partial/trailing/dynamic TP and reconnect/ambiguous results. Native file pickers, actual Windows logon and strict UI reference review remain separate acceptance items.

No claim of profitability, universal broker compatibility, completed REAL-trading acceptance or a defect-free 172-feature product is made.
